Bitcoin LevelDB

Чтение индекса блоков и chainstate Bitcoin Core напрямую с диска

Обновлено в ноябре 2026 г. Первая версия этой страницы без указания авторства воспроизводила ответ Pieter Wuille на Bitcoin Stack Exchange и парсер, опубликованный под тем же вопросом. Оба материала опубликованы там под лицензией CC BY-SA 4.0. Эта версия написана заново нашими словами по исходному коду Bitcoin Core (выпуск v28.1) и вместо копии даёт ссылки на те ответы. В ней также исправлены структура записи и кодировщик varint и добавлен XOR-ключ файлов блоков из Bitcoin Core 28.0.

Дополнительно: ответ Pieter Wuille на вопрос «What are the keys used in the blockchain levelDB?» (перевод: «Какие ключи используются в LevelDB блокчейна?») и другие ответы на этот вопрос (Bitcoin Stack Exchange, CC BY-SA 4.0).

Две базы данных и куча файлов

Bitcoin Core хранит две базы данных LevelDB типа «ключ — значение» рядом со своими сырыми файлами блоков:

  • blocks/index/ — индекс блоков: по одной записи на каждый известный заголовок блока, с указанием, где на диске лежат блок и его данные отката (undo);
  • chainstate/ — множество UTXO текущей лучшей цепи;
  • blocks/blkNNNNN.dat и blocks/revNNNNN.dat — сами блоки в сетевом формате и их данные отката, дописываемые один за другим. Это обычные файлы, а не база данных.

Необязательный индекс транзакций с Bitcoin Core 0.17 хранится в собственной базе данных, indexes/txindex/. LevelDB не позволяет двум программам одновременно открыть одну базу данных, поэтому перед чтением скопируйте её или остановите узел. Для большинства задач проще RPC-вызовы getblock, gettxout и gettxoutsetinfo.

Ключи в chainstate

КлючЗначение
'C' + txid + индекс выхода (varint)один непотраченный выход: высота, является ли он выходом coinbase (coinbase-транзакции), сумма и скрипт (начиная с Bitcoin Core 0.15)

Значения chainstate обфусцированы XOR с ключом, который хранится в той же базе данных (ключ 0x0e 0x00 "obfuscate_key"). Перед декодированием выполните XOR каждого значения с этим ключом, повторяя ключ по длине значения.

Запись индекса блока

Запись 'b' — это последовательность varint, за которой следует 80-байтовый заголовок блока: версия клиента, высота, флаги статуса, число транзакций; затем, только если статус говорит, что данные есть, номер файла и байтовые смещения блока и его данных отката; затем заголовок (версия, хеш предыдущего блока, корень Меркла, время, bits, nonce). varint в Bitcoin Core — это не распространённый LEB128: это big-endian по основанию 128, причём каждый байт продолжения дополнительно прибавляет единицу, так что у каждого числа ровно одна кодировка.

import hashlib

def read_varint(buf, i):
    """Bitcoin Core VARINT (serialize.h ReadVarInt): MSB base-128 with an offset."""
    n = 0
    while True:
        b = buf[i]; i += 1
        n = (n << 7) | (b & 0x7F)
        if b & 0x80:
            n += 1
        else:
            return n, i

def write_varint(n):
    """Inverse of read_varint (serialize.h WriteVarInt)."""
    out = [n & 0x7F]
    while n > 0x7F:
        n = (n >> 7) - 1
        out.append((n & 0x7F) | 0x80)
    return bytes(reversed(out))

BLOCK_HAVE_DATA, BLOCK_HAVE_UNDO = 8, 16

def parse_block_index_value(value):
    """Value of a 'b' + block-hash key in blocks/index (chain.h CDiskBlockIndex)."""
    i, rec = 0, {}
    for field in ('client_version', 'height', 'status', 'tx_count'):
        rec[field], i = read_varint(value, i)
    if rec['status'] & (BLOCK_HAVE_DATA | BLOCK_HAVE_UNDO):
        rec['file'], i = read_varint(value, i)
    if rec['status'] & BLOCK_HAVE_DATA:
        rec['data_pos'], i = read_varint(value, i)
    if rec['status'] & BLOCK_HAVE_UNDO:
        rec['undo_pos'], i = read_varint(value, i)
    header = value[i:i + 80]
    rec['version'] = int.from_bytes(header[0:4], 'little')
    rec['prev_hash'] = header[4:36][::-1].hex()
    rec['merkle_root'] = header[36:68][::-1].hex()
    rec['time'] = int.from_bytes(header[68:72], 'little')
    rec['bits'] = hex(int.from_bytes(header[72:76], 'little'))
    rec['nonce'] = int.from_bytes(header[76:80], 'little')
    rec['block_hash'] = hashlib.sha256(hashlib.sha256(header).digest()).digest()[::-1].hex()
    return rec

Если передать parse_block_index_value значение записи для блока 80 000, функция вернёт высоту 80000, две транзакции, файл 0, bits = 0x1b5bede6 и хеш блока 000000000043a8c0fd1d6f726790caa2a406010d19efd2780db27bdbbd93baf6, который она заново вычисляет по заголовку. Хеши хранятся в порядке байтов little-endian, поэтому для отображения их разворачивают.

Прямое чтение файлов блоков

Каждый блок в файле blk*.dat хранится так: сетевой magic (4 байта), размер блока (4 байта, little-endian), затем сам блок. Начиная с Bitcoin Core 28.0 узел, у которого каталог blocks создаётся с нуля, применяет к этим файлам XOR со случайным 8-байтовым ключом, который хранится в blocks/xor.dat (опция -blocksxor). Старое ПО не может читать такие файлы, пока не применит ключ. Каталог blocks, созданный более ранней версией, сохраняет ключ из одних нулей.

V37Этот метод на практике.

Индекс блоков хранит только заголовки и позиции в файлах; сами блоки — обычные файлы, в которые данные только дописываются. Именно это делает возможным прямое чтение без демона. Графики на странице Реальная сложность этого сайта сделаны так: мы прочитали blocks/blk00000.dat с диска полного узла и по порядку разобрали 80-байтовые заголовки (magic, размер, заголовок, затем nBits и хеш блока — двойной SHA-256) для первых 4032 блоков, без RPC. На узле, развёрнутом с Bitcoin Core 28.0 или новее, сначала примените ключ из blocks/xor.dat. То же свойство лежит в основе проектной работы V37: узел может восстановить зафиксированное состояние по компактным записям на диске и доказать его доказательствами Меркла логарифмического размера; см. краткое изложение Purple Paper, §13 (Проверка выплаты).
