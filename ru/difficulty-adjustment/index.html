Корректировка сложности

Как Bitcoin, Litecoin, Dogecoin и цепочка шар c2pool задают свою сложность

Обновлено в ноябре 2026 г. В первой версии этой страницы говорилось, что перерасчёт сложности в Bitcoin использует «block mediantime» и умножает сложность на отношение временных интервалов. И то и другое неверно: перерасчёт использует метки времени блоков, и пропорционально этому отношению масштабируется именно цель (target), поэтому сложность движется в обратную сторону. Страница переписана по исходному коду Bitcoin Core, добавлены разделы о Litecoin, Dogecoin и цепочке шар c2pool.

Перерасчёт сложности в Bitcoin

Каждые 2016 блоков Bitcoin устанавливает новую цель, чтобы блоки по-прежнему появлялись примерно раз в 10 минут (2016 блоков за 14 дней — целевой интервал, target timespan, T = 1 209 600 с). Шаги — как в src/pow.cpp Bitcoin Core:

  1. Измерение. Фактический интервал — это метка времени (nTime) последнего блока периода минус метка времени первого блока периода, на 2015 блоков раньше. Это собственные метки времени из заголовков блоков, а не их медианное время (MTP).
  2. Ограничение. Фактический интервал ограничивается диапазоном [T/4, 4T], поэтому за один перерасчёт цель меняется не более чем в 4 раза в любую сторону.
  3. Масштабирование цели. новая цель = старая цель × фактический интервал / T. Если блоки шли слишком быстро, отношение меньше 1, цель становится меньше, а сложность — выше.
  4. Верхний предел и кодирование. Новая цель ограничивается сверху наибольшей допустимой для цепи целью (цель «сложности 1», то есть наименьшая сложность) и записывается в следующие заголовки в компактной форме nBits, которая её слегка округляет.

Сложность — это цель сложности 1, делённая на текущую цель, поэтому она меняется обратно пропорционально отношению интервалов.

TARGET_TIMESPAN = 14 * 24 * 60 * 60      # 2016 blocks x 10 minutes
POW_LIMIT = 0xffff << 208                 # difficulty-1 target (nBits 0x1d00ffff)

def bits_to_target(bits):
    exponent, mantissa = bits >> 24, bits & 0x007fffff
    return mantissa << (8 * (exponent - 3)) if exponent >= 3 else mantissa >> (8 * (3 - exponent))

def next_target(last_bits, last_time, first_time):
    """last_time: nTime of the last block of the period.
    first_time: nTime of the block 2015 blocks before it."""
    actual = last_time - first_time
    actual = max(TARGET_TIMESPAN // 4, min(actual, TARGET_TIMESPAN * 4))
    new = bits_to_target(last_bits) * actual // TARGET_TIMESPAN
    return min(new, POW_LIMIT)

def difficulty(target):
    return POW_LIMIT / target

Затем Bitcoin Core кодирует результат обратно в nBits (GetCompact), сохраняя три байта мантиссы. Окно охватывает 2015 интервалов, а не 2016, — известная ошибка на единицу (off-by-one) ещё из первого выпуска, которая теперь стала частью консенсуса. Пример: по меткам времени блоков 30 240 и 32 255 функция даёт nBits = 0x1d00d86a для высоты 32 256 — первое повышение сложности в Bitcoin (сложность около 1,18).

Медианное время (MTP)

Медианное время (MTP, median time past) блока — это медиана меток времени этого блока и десяти предыдущих. Его вычисляет каждый узел; это не поле заголовка. Оно устойчиво к одной неверной или подделанной метке времени, и Bitcoin использует его в двух правилах:

  • метка времени нового блока должна быть позже MTP его родителя (иначе «time-too-old»);
  • блокировки по времени (time-based lock time) сравниваются с MTP, а не с собственной меткой времени блока (BIP 113).

В перерасчёт сложности оно не входит. Вот пример с исходной страницы, который вычисляет MTP вершины цепи через RPC (getblock в Bitcoin Core также возвращает его напрямую как mediantime):

import bitcoin.rpc
def calculate_mediantime():
    proxy = bitcoin.rpc.Proxy()  # Establish connection to Bitcoin Core client
    block_count = proxy.getblockcount()
    if block_count >= 10:
        timestamps = []
        for height in range(block_count, block_count - 11, -1):
            block_hash = proxy.getblockhash(height)
            timestamp = proxy.getblockheader(block_hash).nTime
            timestamps.append(timestamp)
        sorted_timestamps = sorted(timestamps)
        mediantime = sorted_timestamps[5]  # Take the middle timestamp
        return mediantime
    return None  # Return None if there are not enough blocks to calculate mediantime
# Example usage
mediantime = calculate_mediantime()
print(mediantime)

В приведённом фрагменте кода мы подключаемся к работающему клиенту Bitcoin Core через класс bitcoin.rpc.Proxy. Функция calculate_mediantime сначала получает текущее число блоков вызовом getblockcount. Если в блокчейне не меньше 11 блоков (высота вершины 10 или больше), она переходит к вычислению. Она перебирает 11 последних блоков, начиная с текущего, и читает метку времени каждого блока (nTime) из getblockheader. Метки времени сохраняются в списке timestamps. Затем список timestamps сортируется по возрастанию функцией sorted. Наконец, средняя метка времени отсортированного списка (с индексом 5) берётся как mediantime. Функция возвращает mediantime. Если блоков для вычисления mediantime недостаточно, возвращается None.

Litecoin

Litecoin сохраняет правило Bitcoin при интервале между блоками 2,5 минуты: 2016 блоков за 3,5 дня. Одно отличие: после первого периода окно уходит назад на полные 2016 блоков, а не на 2015 (исправление против манипуляций сложностью, которое приписывают Art Forz). Встроенный узел Litecoin в c2pool сам вычисляет следующую цель по синхронизированным заголовкам, с тем же ограничением и по тем же меткам времени.

Dogecoin

У Dogecoin, который c2pool майнит объединённо с Litecoin, до высоты 145 000 окно перерасчёта составляло 4 часа (240 одноминутных блоков). С этой высоты он использует DigiShield, который пересчитывает сложность на каждом блоке. Объединённый майнинг (AuxPoW) начался с высоты 371 337. Встроенный узел Dogecoin в c2pool следует обоим правилам.

Собственная сложность цепочки шар

У цепочки шар P2Pool есть своя сложность, которая задаётся для каждой шары, а не для периода. В c2pool, как и в p2pool:

  • узел оценивает хешрейт пула по недавним шарам и вычисляет цель, которая давала бы одну шару за период шары: 15 секунд в цепочке шар Litecoin, 30 секунд в Bitcoin;
  • результат ограничивается пределами ±10% от цели предыдущей шары, поэтому сложность шар меняется плавно;
  • если за 20 периодов шары (5 минут на Litecoin) не пришло ни одной шары, аварийное правило сложности (из p2pool V36; в исходном p2pool его нет) ослабляет опорную цель: она удваивается за каждые следующие 10 периодов шары, с линейной интерполяцией между ними, и только затем применяется ограничение ±10%. Это не даёт застрять пулу, который внезапно потерял большую часть хешрейта.
V37Цель и сложность; абсолютное расписание.

Сложность и цель обратны друг другу (difficulty = max_target / target), поэтому перерасчёт умножает цель на отношение интервалов, а сложность движется в обратную сторону: более быстрые блоки (меньшее отношение) повышают сложность.

Перерасчёт по окну зависит от меток времени на двух концах этого окна. Абсолютное расписание (в стиле ASERT) вычисляет цель напрямую по опорному блоку и последнему блоку за постоянное время. Оно не проходит по окну, поэтому метки времени внутри окна не могут заставить цель дрейфовать, хотя собственная метка времени последнего блока по-прежнему имеет значение. Bitcoin Cash использует такое расписание с ноября 2020 года. Это кандидат на роль механизма собственной сложности цепочки шар в проектной работе V37; цепочки шар c2pool сегодня используют описанное выше правило для каждой шары.
