LevelDB de Bitcoin

Lire directement sur le disque l’index des blocs et le chainstate de Bitcoin Core

Mis à jour en novembre 2026. La première version de cette page reproduisait, sans attribution, une réponse de Pieter Wuille sur Bitcoin Stack Exchange ainsi qu’un parseur publié sous la même question. Tous deux y sont publiés sous licence CC BY-SA 4.0. Cette version est réécrite avec nos propres mots à partir du code source de Bitcoin Core (version v28.1) et renvoie plutôt vers ces réponses. Elle corrige aussi la structure des enregistrements et l’encodeur de varint, et ajoute la clé XOR des fichiers de blocs de Bitcoin Core 28.0.

Pour aller plus loin : la réponse de Pieter Wuille à « What are the keys used in the blockchain levelDB? » (traduction : « Quelles sont les clés utilisées dans la LevelDB de la blockchain ? »), et les autres réponses à cette question (Bitcoin Stack Exchange, CC BY-SA 4.0).

Deux bases de données et une pile de fichiers

Bitcoin Core tient deux bases de données clé-valeur LevelDB à côté de ses fichiers de blocs bruts :

  • blocks/index/, l’index des blocs : un enregistrement par en-tête de bloc connu, qui indique où se trouvent sur le disque le bloc et ses données d’annulation (undo) ;
  • chainstate/, l’ensemble UTXO de la meilleure chaîne actuelle ;
  • blocks/blkNNNNN.dat et blocks/revNNNNN.dat : les blocs eux-mêmes, au format réseau, et leurs données d’annulation, ajoutés les uns à la suite des autres. Ce sont de simples fichiers, pas une base de données.

L’index des transactions, facultatif, a sa propre base de données, indexes/txindex/, depuis Bitcoin Core 0.17. LevelDB n’autorise pas deux programmes à ouvrir une base en même temps : copiez-la, ou arrêtez le nœud, avant de la lire. Pour la plupart des questions, les appels RPC getblock, gettxout et gettxoutsetinfo sont plus simples.

'f' + numéro de fichier sur 4 octetsstatistiques d’un fichier de blocs : nombre de blocs, tailles des fichiers, hauteurs et horodatages minimaux et maximaux

'R'positionnée pendant une réindexation
'F' + nom du drapeauun drapeau booléen nommé

Les clés du chainstate

CléValeur
'C' + txid + index de sortie (varint)une sortie non dépensée : hauteur, s’il s’agit ou non d’une sortie coinbase, montant et script (depuis Bitcoin Core 0.15)
'c' + txidl’ancien format par transaction (avant 0.15) ; on ne le rencontre qu’en mettant à niveau une ancienne base
'B'le hash du bloc jusqu’auquel l’ensemble UTXO est complet
'H'les blocs de tête lorsqu’une écriture sur disque (flush) est interrompue

Les valeurs du chainstate sont obscurcies par XOR avec une clé stockée dans la même base (clé 0x0e 0x00 "obfuscate_key"). Appliquez à chaque valeur un XOR avec la clé, répétée, avant de la décoder.

L’enregistrement d’index de bloc

Un enregistrement 'b' est une suite de varints suivie de l’en-tête de bloc de 80 octets : version du client, hauteur, drapeaux d’état, nombre de transactions ; puis, seulement si l’état indique que les données sont présentes, le numéro de fichier et les positions en octets du bloc et de ses données d’annulation ; puis l’en-tête (version, hash précédent, racine de Merkle, horodatage, bits, nonce). Le varint de Bitcoin Core n’est pas le LEB128 courant : c’est une base 128 big-endian, et chaque octet de continuation ajoute en outre un, de sorte que chaque nombre a exactement un encodage.

import hashlib

def read_varint(buf, i):
    """Bitcoin Core VARINT (serialize.h ReadVarInt): MSB base-128 with an offset."""
    n = 0
    while True:
        b = buf[i]; i += 1
        n = (n << 7) | (b & 0x7F)
        if b & 0x80:
            n += 1
        else:
            return n, i

def write_varint(n):
    """Inverse of read_varint (serialize.h WriteVarInt)."""
    out = [n & 0x7F]
    while n > 0x7F:
        n = (n >> 7) - 1
        out.append((n & 0x7F) | 0x80)
    return bytes(reversed(out))

BLOCK_HAVE_DATA, BLOCK_HAVE_UNDO = 8, 16

def parse_block_index_value(value):
    """Value of a 'b' + block-hash key in blocks/index (chain.h CDiskBlockIndex)."""
    i, rec = 0, {}
    for field in ('client_version', 'height', 'status', 'tx_count'):
        rec[field], i = read_varint(value, i)
    if rec['status'] & (BLOCK_HAVE_DATA | BLOCK_HAVE_UNDO):
        rec['file'], i = read_varint(value, i)
    if rec['status'] & BLOCK_HAVE_DATA:
        rec['data_pos'], i = read_varint(value, i)
    if rec['status'] & BLOCK_HAVE_UNDO:
        rec['undo_pos'], i = read_varint(value, i)
    header = value[i:i + 80]
    rec['version'] = int.from_bytes(header[0:4], 'little')
    rec['prev_hash'] = header[4:36][::-1].hex()
    rec['merkle_root'] = header[36:68][::-1].hex()
    rec['time'] = int.from_bytes(header[68:72], 'little')
    rec['bits'] = hex(int.from_bytes(header[72:76], 'little'))
    rec['nonce'] = int.from_bytes(header[76:80], 'little')
    rec['block_hash'] = hashlib.sha256(hashlib.sha256(header).digest()).digest()[::-1].hex()
    return rec

Si on lui fournit la valeur de l’enregistrement du bloc 80 000, parse_block_index_value renvoie la hauteur 80000, deux transactions, le fichier 0, bits = 0x1b5bede6 et le hash de bloc 000000000043a8c0fd1d6f726790caa2a406010d19efd2780db27bdbbd93baf6, qu’elle recalcule à partir de l’en-tête. Les hashs sont stockés en ordre d’octets little-endian ; on les inverse donc pour l’affichage.

Lire directement les fichiers de blocs

Chaque bloc d’un fichier blk*.dat est stocké sous la forme des octets magiques du réseau (4 octets), de la taille du bloc (4 octets, little-endian), puis du bloc. Depuis Bitcoin Core 28.0, un nœud dont le répertoire des blocs est créé à neuf applique un XOR à ces fichiers avec une clé aléatoire de 8 octets conservée dans blocks/xor.dat (option -blocksxor). Un logiciel plus ancien ne peut pas lire ces fichiers tant qu’il n’applique pas la clé. Un répertoire des blocs créé par une version antérieure garde une clé entièrement nulle.

V37Cette méthode en pratique.

L’index des blocs ne contient que les en-têtes et les positions dans les fichiers ; les blocs eux-mêmes sont de simples fichiers en ajout seul. C’est ce qui rend possibles des lectures directes, sans démon. Les graphiques de la page Difficulté réelle de ce site ont été réalisés ainsi : nous avons lu blocks/blk00000.dat sur le disque d’un nœud complet et analysé dans l’ordre les en-têtes de 80 octets (octets magiques, taille, en-tête, puis nBits et le hash de bloc double SHA-256) des 4032 premiers blocs, sans RPC. Sur un nœud installé avec Bitcoin Core 28.0 ou ultérieur, appliquez d’abord la clé de blocks/xor.dat. La même propriété sous-tend les travaux de conception de V37 : un nœud peut reconstruire l’état engagé à partir d’enregistrements compacts sur disque et le prouver par des preuves de Merkle de taille logarithmique ; voir le résumé du Purple Paper, §13 (Vérifier le paiement).
