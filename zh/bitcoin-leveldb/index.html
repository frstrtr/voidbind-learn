Bitcoin LevelDB

直接从磁盘读取 Bitcoin Core 的区块索引和 chainstate

2026 年 11 月更新。本页第一版未注明出处地转载了 Pieter Wuille 在 Bitcoin Stack Exchange 上的一个回答，以及同一问题下发布的一个解析器。两者在该网站上均以 CC BY-SA 4.0 发布。本版依据 Bitcoin Core 源代码（v28.1 版本）用我们自己的话重写，并改为链接到这些回答。本版还更正了记录布局和 varint 编码器，并补充了 Bitcoin Core 28.0 的区块文件 XOR 密钥。

延伸阅读：Pieter Wuille 的回答（问题为“What are the keys used in the blockchain levelDB?”（译文：“区块链 levelDB 中使用了哪些键？”）），以及该问题下的其他回答（Bitcoin Stack Exchange，CC BY-SA 4.0）。

两个数据库和一堆文件

Bitcoin Core 在原始区块文件旁边维护两个 LevelDB 键值数据库：

  • blocks/index/，即区块索引：每个已知区块头对应一条记录，说明该区块及其撤销数据在磁盘上的位置；
  • chainstate/，即当前最佳链的 UTXO 集；
  • blocks/blkNNNNN.dat 和 blocks/revNNNNN.dat：区块本身（网络格式）及其撤销数据，依次追加写入。这些是普通文件，不是数据库。

可选的交易索引自 Bitcoin Core 0.17 起存放在单独的数据库 indexes/txindex/ 中。LevelDB 不允许两个程序同时打开同一个数据库，所以读取之前要先复制它，或者先停止节点。对大多数问题来说，使用 RPC 调用 getblock、gettxout 和 gettxoutsetinfo 更简单。

区块索引中的键

键值
'b' + 32 字节区块哈希区块索引记录（见下文）
'f' + 4 字节文件编号一个区块文件的统计信息：区块数、文件大小、最低和最高的高度与时间
'l'最后使用的区块文件编号
'R'重建索引（reindex）进行期间设置
'F' + 标志名一个具名的布尔标志

chainstate 中的键

键值
'C' + txid + 输出索引（varint）一个未花费输出：高度、是否为 coinbase 输出、金额和脚本（自 Bitcoin Core 0.15 起）
'c' + txid旧的按交易存储的格式（0.15 之前）；如果 chainstate 中仍有这种记录，Bitcoin Core v28.1 会拒绝使用它，并要求执行 -reindex-chainstate
'B'UTXO 集已完整对应到的那个区块的哈希
'H'刷写被中断时的头部区块

chainstate 的值经过 XOR 混淆，密钥存放在同一个数据库中（键为 0x0e 0x00 "obfuscate_key"）。解码之前，先把每个值与重复排列的密钥做 XOR。

区块索引记录

一条 'b' 记录由一串 varint 加上 80 字节的区块头组成：客户端版本、高度、状态标志、交易数；然后，仅当状态表明数据存在时，才有文件编号以及区块和撤销数据的字节偏移量；最后是区块头（版本、前一区块哈希、默克尔根、时间、bits、nonce）。Bitcoin Core 的 varint 不是常见的 LEB128：它是大端序的 128 进制，并且每个后续字节还会额外加一，因此每个数都只有唯一一种编码。

import hashlib

def read_varint(buf, i):
    """Bitcoin Core VARINT (serialize.h ReadVarInt): MSB base-128 with an offset."""
    n = 0
    while True:
        b = buf[i]; i += 1
        n = (n << 7) | (b & 0x7F)
        if b & 0x80:
            n += 1
        else:
            return n, i

def write_varint(n):
    """Inverse of read_varint (serialize.h WriteVarInt)."""
    out = [n & 0x7F]
    while n > 0x7F:
        n = (n >> 7) - 1
        out.append((n & 0x7F) | 0x80)
    return bytes(reversed(out))

BLOCK_HAVE_DATA, BLOCK_HAVE_UNDO = 8, 16

def parse_block_index_value(value):
    """Value of a 'b' + block-hash key in blocks/index (chain.h CDiskBlockIndex)."""
    i, rec = 0, {}
    for field in ('client_version', 'height', 'status', 'tx_count'):
        rec[field], i = read_varint(value, i)
    if rec['status'] & (BLOCK_HAVE_DATA | BLOCK_HAVE_UNDO):
        rec['file'], i = read_varint(value, i)
    if rec['status'] & BLOCK_HAVE_DATA:
        rec['data_pos'], i = read_varint(value, i)
    if rec['status'] & BLOCK_HAVE_UNDO:
        rec['undo_pos'], i = read_varint(value, i)
    header = value[i:i + 80]
    rec['version'] = int.from_bytes(header[0:4], 'little')
    rec['prev_hash'] = header[4:36][::-1].hex()
    rec['merkle_root'] = header[36:68][::-1].hex()
    rec['time'] = int.from_bytes(header[68:72], 'little')
    rec['bits'] = hex(int.from_bytes(header[72:76], 'little'))
    rec['nonce'] = int.from_bytes(header[76:80], 'little')
    rec['block_hash'] = hashlib.sha256(hashlib.sha256(header).digest()).digest()[::-1].hex()
    return rec

把区块 80,000 的记录值传给 parse_block_index_value，它返回高度 80000、两笔交易、文件 0、bits = 0x1b5bede6，以及它根据区块头重新计算出的区块哈希 000000000043a8c0fd1d6f726790caa2a406010d19efd2780db27bdbbd93baf6。哈希以小端字节序存储，因此显示时要反转字节顺序。

直接读取区块文件

blk*.dat 文件中的每个区块依次存储为：网络魔数（4 字节）、区块大小（4 字节，小端序），然后是区块本身。自 Bitcoin Core 28.0 起，如果节点的 blocks 目录是新建的，这些文件会用一个 8 字节的随机密钥做 XOR，密钥保存在 blocks/xor.dat 中（选项 -blocksxor）。旧软件在应用该密钥之前无法读取这类文件。由更早版本创建的 blocks 目录保持全零密钥。

V37这种方法的实际应用。

区块索引只存放区块头、文件位置和少量状态数据；区块本身是只追加写入的普通文件。正因如此，才能直接读取而无需守护进程。本站的真实难度图表就是这样制作的：我们从一个全节点的磁盘上读取 blocks/blk00000.dat，按顺序解析前 4,032 个区块的 80 字节区块头（魔数、大小、区块头，然后是 nBits 和两次 SHA-256 得到的区块哈希），没有使用 RPC。对于用 Bitcoin Core 28.0 或更高版本建立的节点，要先应用 blocks/xor.dat 中的密钥。V37 设计工作也基于同样的特性：节点可以从紧凑的磁盘记录中重建已承诺的状态，并用对数大小的默克尔证明来证明它；参见 Purple Paper 摘要第 13 节（验证支付）。
