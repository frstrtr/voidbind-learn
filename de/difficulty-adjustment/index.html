Schwierigkeitsanpassung

Wie Bitcoin, Litecoin, Dogecoin und die c2pool-Share-Chain ihre Schwierigkeit festlegen

Aktualisiert im November 2026. Die erste Fassung dieser Seite sagte, das Retarget (Neuberechnung) von Bitcoin verwende die „block mediantime“ und multipliziere die Schwierigkeit mit dem Verhältnis der Zeitspannen. Beides ist falsch: Das Retarget verwendet die Zeitstempel der Blöcke, und es ist das Target, das mit dem Verhältnis skaliert wird, sodass sich die Schwierigkeit in die Gegenrichtung bewegt. Die Seite ist anhand des Quellcodes von Bitcoin Core neu geschrieben, und Abschnitte zu Litecoin, Dogecoin und der c2pool-Share-Chain sind hinzugekommen.

Das Retarget von Bitcoin

Alle 2016 Blöcke legt Bitcoin ein neues Target fest, damit Blöcke weiterhin etwa alle 10 Minuten eintreffen (2016 Blöcke in 14 Tagen, die Soll-Zeitspanne (target timespan) T = 1.209.600 s). Die Schritte, wie in src/pow.cpp von Bitcoin Core:

  1. Messen. Die tatsächliche Zeitspanne ist der Zeitstempel (nTime) des letzten Blocks der Periode minus den Zeitstempel des ersten Blocks der Periode, 2015 Blöcke früher. Das sind die eigenen Header-Zeitstempel der Blöcke, nicht ihre Median Time Past.
  2. Begrenzen. Die tatsächliche Zeitspanne wird auf den Bereich [T/4, 4T] beschränkt, sodass ein Retarget das Target höchstens um den Faktor 4 in die eine oder andere Richtung verschiebt.
  3. Target skalieren. Neues Target = altes Target × tatsächliche Zeitspanne / T. Zu schnell gekommene Blöcke ergeben ein Verhältnis unter 1, ein kleineres Target und eine höhere Schwierigkeit.
  4. Deckeln und kodieren. Das neue Target wird auf das größte erlaubte Target der Chain begrenzt (das „Schwierigkeit 1“-Target, also die niedrigste Schwierigkeit) und in den folgenden Headern in der kompakten nBits-Form gespeichert, die es leicht rundet.

Die Schwierigkeit ist das Schwierigkeit-1-Target geteilt durch das aktuelle Target; sie ändert sich also um den Kehrwert des Zeitspannen-Verhältnisses.

TARGET_TIMESPAN = 14 * 24 * 60 * 60      # 2016 blocks x 10 minutes
POW_LIMIT = 0xffff << 208                 # difficulty-1 target (nBits 0x1d00ffff)

def bits_to_target(bits):
    exponent, mantissa = bits >> 24, bits & 0x007fffff
    return mantissa << (8 * (exponent - 3)) if exponent >= 3 else mantissa >> (8 * (3 - exponent))

def next_target(last_bits, last_time, first_time):
    """last_time: nTime of the last block of the period.
    first_time: nTime of the block 2015 blocks before it."""
    actual = last_time - first_time
    actual = max(TARGET_TIMESPAN // 4, min(actual, TARGET_TIMESPAN * 4))
    new = bits_to_target(last_bits) * actual // TARGET_TIMESPAN
    return min(new, POW_LIMIT)

def difficulty(target):
    return POW_LIMIT / target

Bitcoin Core kodiert das Ergebnis anschließend wieder in nBits (GetCompact), das drei Bytes Mantisse behält. Das Fenster umfasst 2015 Intervalle statt 2016, ein bekannter Off-by-one-Fehler aus dem ersten Release, der inzwischen Konsens ist. Beispiel: Mit den Zeitstempeln der Blöcke 30.240 und 32.255 liefert die Funktion nBits = 0x1d00d86a für Höhe 32.256, die erste Erhöhung der Schwierigkeit bei Bitcoin (Schwierigkeit etwa 1,18).

Median Time Past

Die Median Time Past (MTP) eines Blocks ist der Median der Zeitstempel dieses Blocks und der zehn Blöcke davor. Jeder Knoten berechnet sie; sie ist kein Header-Feld. Sie ist robust gegen einen einzelnen falschen oder manipulierten Zeitstempel, und Bitcoin verwendet sie für zwei Regeln:

  • Der Zeitstempel eines neuen Blocks muss später sein als die MTP seines Elternblocks (sonst „time-too-old“);
  • zeitbasierte Lock-Times werden mit der MTP verglichen, nicht mit dem eigenen Zeitstempel des Blocks (BIP 113).

In das Retarget der Schwierigkeit geht sie nicht ein. Hier das Beispiel der ursprünglichen Seite, das die MTP der Chain-Spitze per RPC berechnet (getblock von Bitcoin Core liefert sie auch direkt als mediantime):

import bitcoin.rpc
 def calculate_mediantime():
    proxy = bitcoin.rpc.Proxy()  # Establish connection to Bitcoin Core client
    block_count = proxy.getblockcount()
    if block_count >= 11:
        timestamps = []
        for height in range(block_count, block_count - 11, -1):
            block_hash = proxy.getblockhash(height)
            block = proxy.getblock(block_hash)
            timestamp = block['time']
            timestamps.append(timestamp)
        sorted_timestamps = sorted(timestamps)
        mediantime = sorted_timestamps[5]  # Take the middle timestamp
        return mediantime
    return None  # Return None if there are not enough blocks to calculate mediantime
 # Example usage
 mediantime = calculate_mediantime()
 print(mediantime)

Im obigen Code-Ausschnitt stellen wir mit der Klasse bitcoin.rpc.Proxy eine Verbindung zu einem laufenden Bitcoin-Core-Client her. Die Funktion calculate_mediantime ermittelt zuerst mit getblockcount die aktuelle Blockanzahl. Gibt es mindestens 11 Blöcke in der Blockchain, fährt sie mit der Berechnung fort. Sie durchläuft die letzten 11 Blöcke, beginnend mit dem aktuellen Block, und holt mit getblock jeweils den Zeitstempel des Blocks. Die Zeitstempel werden in der Liste timestamps gespeichert. Diese Liste wird dann mit der Funktion sorted aufsteigend sortiert. Schließlich wird der mittlere Zeitstempel der sortierten Liste (an Index 5) als mediantime genommen. Die Funktion gibt mediantime zurück. Gibt es nicht genug Blöcke, um mediantime zu berechnen, wird None zurückgegeben.

Litecoin

Litecoin behält die Regel von Bitcoin mit einem Blockabstand von 2,5 Minuten bei: 2016 Blöcke in 3,5 Tagen. Ein Unterschied: Nach der ersten Periode reicht das Fenster volle 2016 Blöcke zurück statt 2015 (eine Korrektur gegen Manipulation der Schwierigkeit, die Art Forz zugeschrieben wird). Der eingebettete Litecoin-Knoten von c2pool berechnet das nächste Target selbst aus den Headern, die er synchronisiert hat, mit derselben Begrenzung und denselben Zeitstempeln.

Dogecoin

Dogecoin, das c2pool per Merged Mining zusammen mit Litecoin mined, hatte bis Höhe 145.000 ein Retarget-Fenster von 4 Stunden (240 Blöcke zu je einer Minute). Ab dieser Höhe verwendet es DigiShield, das bei jedem Block neu berechnet. Merged Mining (AuxPoW) begann bei Höhe 371.337. Der eingebettete Dogecoin-Knoten von c2pool folgt beiden Regeln.

Die eigene Schwierigkeit der Share-Chain

Eine P2Pool-Share-Chain hat eine eigene Schwierigkeit, festgelegt pro Share statt pro Periode. In c2pool gilt, wie in p2pool:

  • Der Knoten schätzt die Rate des Pools aus den letzten Shares und berechnet das Target, das einen Share pro Share-Periode ergäbe: 15 Sekunden auf der Litecoin-Share-Chain, 30 Sekunden auf Bitcoin;
  • das Ergebnis wird auf ±10 % um das Target des vorigen Shares begrenzt, sodass sich die Share-Schwierigkeit gleichmäßig bewegt;
  • ist 20 Share-Perioden lang (5 Minuten auf Litecoin) kein Share eingetroffen, lockert eine Notfall-Schwierigkeitsregel das Referenz-Target: Es verdoppelt sich je weitere 10 Share-Perioden, dazwischen linear interpoliert, bevor die Begrenzung auf ±10 % greift. So bleibt ein Pool, der plötzlich den größten Teil seiner Hashrate verloren hat, nicht stecken.
V37Target vs. Schwierigkeit, und ein absoluter Zeitplan.

Schwierigkeit und Target sind zueinander invers (difficulty = max_target / target), daher multipliziert das Retarget das Target mit dem Zeitspannen-Verhältnis, und die Schwierigkeit bewegt sich in die Gegenrichtung: Schnellere Blöcke (ein kleineres Verhältnis) erhöhen die Schwierigkeit.

Für ein Retarget die Chain zurückzulaufen, ist bei langen Fenstern aufwendig. Ein absoluter Zeitplan (nach Art von ASERT) berechnet das Target in konstanter Zeit direkt aus einem Ankerblock und dem jüngsten Block. Er durchläuft kein Fenster, daher können Zeitstempel innerhalb eines Fensters das Target nicht abdriften lassen, auch wenn der eigene Zeitstempel des jüngsten Blocks weiterhin eine Rolle spielt. Bitcoin Cash verwendet einen solchen Zeitplan seit November 2020. Er ist in der V37-Designarbeit ein Kandidat für die eigene Schwierigkeit einer Share-Chain; die c2pool-Share-Chains verwenden heute die oben beschriebene Regel pro Share.
