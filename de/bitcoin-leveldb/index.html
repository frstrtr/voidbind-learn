Bitcoin LevelDB

Block-Index und Chainstate von Bitcoin Core direkt von der Festplatte lesen

Aktualisiert im November 2026. Die erste Fassung dieser Seite gab ohne Quellenangabe eine Antwort von Pieter Wuille auf Bitcoin Stack Exchange und einen unter derselben Frage veröffentlichten Parser wieder. Beide sind dort unter CC BY-SA 4.0 veröffentlicht. Diese Fassung ist in unseren eigenen Worten anhand des Quellcodes von Bitcoin Core (Release v28.1) neu geschrieben und verlinkt stattdessen auf diese Antworten. Außerdem korrigiert sie den Aufbau der Datensätze und den Varint-Encoder und ergänzt den XOR-Schlüssel für Blockdateien aus Bitcoin Core 28.0.

Weiterführend: die Antwort von Pieter Wuille auf „What are the keys used in the blockchain levelDB?“ (Übersetzung: „Welche Schlüssel werden in der LevelDB der Blockchain verwendet?“) und die anderen Antworten auf diese Frage (Bitcoin Stack Exchange, CC BY-SA 4.0).

Zwei Datenbanken und ein Haufen Dateien

Bitcoin Core führt neben seinen rohen Blockdateien zwei LevelDB-Key-Value-Datenbanken:

  • blocks/index/, der Block-Index: ein Datensatz pro bekanntem Block-Header, der angibt, wo der Block und seine Undo-Daten auf der Festplatte liegen;
  • chainstate/, die UTXO-Menge der aktuell besten Chain;
  • blocks/blkNNNNN.dat und blocks/revNNNNN.dat: die Blöcke selbst im Netzwerkformat und ihre Undo-Daten, nacheinander angehängt. Das sind gewöhnliche Dateien, keine Datenbank.

Der optionale Transaktionsindex liegt seit Bitcoin Core 0.17 in einer eigenen Datenbank, indexes/txindex/. LevelDB erlaubt nicht, dass zwei Programme eine Datenbank gleichzeitig öffnen; kopiere sie also oder stoppe den Knoten, bevor du liest. Für die meisten Fragen sind die RPC-Aufrufe getblock, gettxout und gettxoutsetinfo einfacher.

Schlüssel im Block-Index

SchlüsselWert
'b' + 32-Byte-Block-Hashder Block-Index-Datensatz (siehe unten)
'f' + 4-Byte-DateinummerStatistik einer Blockdatei: Anzahl der Blöcke, Dateigrößen, niedrigste und höchste Höhe und Zeit
'l'die Nummer der zuletzt verwendeten Blockdatei
'R'gesetzt, während ein Reindex läuft
'F' + Flag-Nameein benanntes boolesches Flag

Schlüssel im Chainstate

SchlüsselWert
'C' + txid + Output-Index (Varint)ein unverbrauchter Output: Höhe, ob es ein Coinbase-Output ist, Betrag und Script (ab Bitcoin Core 0.15)
'c' + txiddas ältere Format pro Transaktion (vor 0.15); nur beim Upgrade einer alten Datenbank anzutreffen
'B'der Hash des Blocks, bis zu dem die UTXO-Menge vollständig ist
'H'die Head-Blöcke, während ein Flush unterbrochen ist

Die Werte im Chainstate sind per XOR verschleiert, mit einem Schlüssel, der in derselben Datenbank liegt (Schlüssel 0x0e 0x00 "obfuscate_key"). Verknüpfe jeden Wert per XOR mit dem wiederholten Schlüssel, bevor du ihn dekodierst.

Der Block-Index-Datensatz

Ein 'b'-Datensatz ist eine Folge von Varints, gefolgt vom 80-Byte-Block-Header: Client-Version, Höhe, Status-Flags, Anzahl der Transaktionen; dann, nur wenn der Status angibt, dass die Daten vorhanden sind, die Dateinummer und die Byte-Offsets des Blocks und seiner Undo-Daten; dann der Header (Version, vorheriger Hash, Merkle-Root, Zeit, Bits, Nonce). Der Varint von Bitcoin Core ist nicht das übliche LEB128: Er ist Big-Endian zur Basis 128, und jedes Fortsetzungsbyte addiert zusätzlich eins, sodass jede Zahl genau eine Kodierung hat.

import hashlib

def read_varint(buf, i):
    """Bitcoin Core VARINT (serialize.h ReadVarInt): MSB base-128 with an offset."""
    n = 0
    while True:
        b = buf[i]; i += 1
        n = (n << 7) | (b & 0x7F)
        if b & 0x80:
            n += 1
        else:
            return n, i

def write_varint(n):
    """Inverse of read_varint (serialize.h WriteVarInt)."""
    out = [n & 0x7F]
    while n > 0x7F:
        n = (n >> 7) - 1
        out.append((n & 0x7F) | 0x80)
    return bytes(reversed(out))

BLOCK_HAVE_DATA, BLOCK_HAVE_UNDO = 8, 16

def parse_block_index_value(value):
    """Value of a 'b' + block-hash key in blocks/index (chain.h CDiskBlockIndex)."""
    i, rec = 0, {}
    for field in ('client_version', 'height', 'status', 'tx_count'):
        rec[field], i = read_varint(value, i)
    if rec['status'] & (BLOCK_HAVE_DATA | BLOCK_HAVE_UNDO):
        rec['file'], i = read_varint(value, i)
    if rec['status'] & BLOCK_HAVE_DATA:
        rec['data_pos'], i = read_varint(value, i)
    if rec['status'] & BLOCK_HAVE_UNDO:
        rec['undo_pos'], i = read_varint(value, i)
    header = value[i:i + 80]
    rec['version'] = int.from_bytes(header[0:4], 'little')
    rec['prev_hash'] = header[4:36][::-1].hex()
    rec['merkle_root'] = header[36:68][::-1].hex()
    rec['time'] = int.from_bytes(header[68:72], 'little')
    rec['bits'] = hex(int.from_bytes(header[72:76], 'little'))
    rec['nonce'] = int.from_bytes(header[76:80], 'little')
    rec['block_hash'] = hashlib.sha256(hashlib.sha256(header).digest()).digest()[::-1].hex()
    return rec

Mit dem Wert des Datensatzes für Block 80.000 gefüttert, liefert parse_block_index_value Höhe 80000, zwei Transaktionen, Datei 0, bits = 0x1b5bede6 und den Block-Hash 000000000043a8c0fd1d6f726790caa2a406010d19efd2780db27bdbbd93baf6, den die Funktion aus dem Header neu berechnet. Hashes werden in Little-Endian-Bytereihenfolge gespeichert und für die Anzeige daher umgedreht.

Die Blockdateien direkt lesen

Jeder Block in einer blk*.dat-Datei wird gespeichert als Netzwerk-Magic (4 Bytes), Blockgröße (4 Bytes, Little-Endian), dann der Block. Seit Bitcoin Core 28.0 verknüpft ein Knoten, dessen Blocks-Verzeichnis neu angelegt wird, diese Dateien per XOR mit einem zufälligen 8-Byte-Schlüssel, der in blocks/xor.dat liegt (Option -blocksxor). Ältere Software kann solche Dateien erst lesen, wenn sie den Schlüssel anwendet. Ein Blocks-Verzeichnis, das von einer früheren Version angelegt wurde, behält einen Schlüssel aus lauter Nullen.

V37Diese Methode in der Praxis.

Der Block-Index enthält nur Header und Dateipositionen; die Blöcke selbst sind gewöhnliche Dateien, an die nur angehängt wird. Das macht direktes Lesen ohne Daemon möglich. Die Diagramme auf der Seite Echte Schwierigkeit sind auf diese Weise entstanden: Wir haben blocks/blk00000.dat von der Festplatte eines Full Nodes gelesen und für die ersten 4.032 Blöcke die 80-Byte-Header der Reihe nach geparst (Magic, Größe, Header, dann nBits und der doppelte SHA-256-Block-Hash), ohne RPC. Auf einem Knoten, der mit Bitcoin Core 28.0 oder neuer eingerichtet wurde, wende zuerst den Schlüssel aus blocks/xor.dat an. Dieselbe Eigenschaft liegt der V37-Designarbeit zugrunde: Ein Knoten kann festgeschriebenen Zustand aus kompakten Datensätzen auf der Festplatte wiederherstellen und ihn mit Merkle-Proofs logarithmischer Größe belegen; siehe die Zusammenfassung des Purple Paper, §13 (Zahlungen überprüfen).
