Taproot-Coinbase

Taproot-Outputs in einer Coinbase-Transaktion und was sie für einen dezentralen Pool leisten können und was nicht

Taproot-Adressen in der Coinbase-Transaktion zu verwenden, um mehrere Outputs abzubilden oder mehrere Transaktionen zu ermöglichen, ist technisch machbar und bietet einige Vorteile bei Effizienz und Privatsphäre.

Eine einzige Taproot-Adresse für mehrere Outputs

Eine Taproot-Adresse, abgeleitet aus einem Schnorr-Public-Key in Kombination mit MAST (Merkelized Abstract Syntax Trees), kann komplexe Ausgabebedingungen hinter einer einzigen Adresse verbergen. Damit ließen sich potenziell mehrere Parteien aus einem einzigen Taproot-Output bezahlen, indem man unterschiedliche Bedingungen in den Script-Path-Spend dieses Outputs kodiert. Allerdings müssen die jeweiligen Bedingungen jeder Partei erfüllt sein, damit sie ihren Anteil ausgeben kann; diese Bedingungen wären in der Script-Logik selbst festgelegt.

Mehrere Taproot-Adressen in der Coinbase

Man kann auch mehrere Taproot-Adressen direkt in den Outputs einer Coinbase-Transaktion verwenden, ähnlich wie mehrere Legacy- oder SegWit-Adressen. Jeder Output kann auf eine andere Taproot-Adresse zeigen. So kann die Transaktion die Block-Belohnung an mehrere Empfänger oder Adressen verteilen, jede mit eigenen komplexen Ausgabebedingungen, die über Taproot kodiert sind.

Vorteile

  • Privatsphäre: Taproot-Adressen können mehr Privatsphäre bieten, da die Bedingungen, unter denen die Coins ausgegeben werden, verborgen bleiben können, bis sie relevant werden (d. h. wenn sie tatsächlich in einer Transaktion verwendet werden).
  • Effizienz: Taproot kann Schnorr-Signaturen nutzen, die im Vergleich zu den ECDSA-Signaturen klassischer Bitcoin-Transaktionen platzsparender und schneller zu verifizieren sind.

Hinweise zur Verwendung

Wenn man mit einer einzigen Taproot-Adresse mehrere Zahlungsbedingungen kodiert, ist es entscheidend, die Bedingungen so zu strukturieren, dass sie das Ausgeben der Mittel nicht unnötig verkomplizieren. Der Kerngedanke ist, die Effizienz der Transaktion zu erhalten und zugleich die Fähigkeit von Taproot zu nutzen, komplexe Transaktionen zu vereinfachen.

Zusammengefasst: Man kann eine oder zwei Taproot-Adressen in einer Coinbase-Transaktion verwenden, entweder indem mehrere Outputs auf verschiedene Taproot-Adressen zeigen oder indem eine Taproot-Adresse mehrere Ausgabebedingungen innerhalb eines einzigen Outputs abdeckt. Dieser Aufbau kann besonders für Mining-Pools nützlich sein, die Auszahlungen vereinfachen und Privatsphäre und Sicherheit der Transaktionen verbessern wollen.

Eine Taproot-Adresse ist ein Bitcoin-Adresstyp, der mit „bc1p“ beginnt und im Bech32m-Format kodiert ist. Anders als klassische Adressen kann eine Taproot-Adresse komplexere Scripts platzsparender und datenschutzfreundlicher darstellen, durch die Kombination aus Schnorr-Signatur und MAST.

Beispiel für den Aufbau einer Taproot-Transaktion

Inputs

  • Input 1: Txid (Transaktions-ID einer früheren Transaktion); Vout (Output-Index in der früheren Transaktion); ScriptSig: leer (ein Taproot-Spend trägt seine Daten im Witness); Witness: enthält die Schnorr-Signatur und gegebenenfalls weitere Bestandteile, falls der Script-Path genutzt wird.
  • Input 2: Ein weiterer Input im selben Format.

Outputs

  • Output 1: Value (zu sendender Betrag in Bitcoin); ScriptPubKey: OP_1 <32-byte x-only output key> (34 Bytes: 51 20 …), das Format eines Taproot-Output-Scripts, das erst dann komplex wird, wenn ein Script-Path-Spend ausgelöst wird.
  • Output 2: Ein weiterer Output mit seinem Betrag und Taproot-Script.

Schritt für Schritt

Txid und Vout: Jeder Input verweist auf den Output einer früheren Transaktion. Diese Outputs werden durch die Inputs der neuen Transaktion ausgegeben.

ScriptSig: Taproot-Transaktionen haben in der Regel ein leeres ScriptSig, weil die Script-Validierung auf dem Witness-Teil der Transaktion beruht.

Witness: Enthält die Schnorr-Signatur, die den Besitz des Taproot-Public-Keys belegt. Werden komplexe Bedingungen genutzt (Script-Path-Spend), stehen hier die betreffenden Scripts und Signaturen.

Outputs: Jeder Output gibt an, wie viele Bitcoin gesendet werden und an welche Adresse (dargestellt durch den Taproot-Public-Key). Das ScriptPubKey für Taproot-Outputs ist auf OP_1 <Taproot public key> vereinfacht, sodass mögliche komplexe Bedingungen in den Witness-Daten behandelt werden können, falls ein Script-Path-Spend aktiviert wird.

Dieser Aufbau erlaubt ausgefeilte Bedingungen in den Outputs, die erst sichtbar werden, wenn sie gezielt aktiviert werden (z. B. bei Rückerstattungen, Vereinbarungen zwischen mehreren Parteien usw.), und verbessert so Privatsphäre und Flexibilität. Die eigentliche Stärke von Taproot liegt darin, dass – solange eine Transaktion nicht angefochten wird oder die Bedingungen nicht komplex sind – nur der Key-Path-Spend (also eine einzelne Signatur) offengelegt werden muss; andere mögliche Bedingungen bleiben verborgen, und die Transaktionen sehen aus wie gewöhnliche Single-Signature-Transaktionen. Dies ist nur ein konzeptionelles Beispiel. Eine echte Transaktion müsste den Vorgaben der jeweiligen Software- oder Hardware-Wallet entsprechen, die Taproot unterstützt.

Die Coinbase-Belohnung an eine Taproot-Adresse senden

Es ist ohne Weiteres möglich, die Belohnung der Coinbase-Transaktion in Transaktion 0 (der Coinbase-Transaktion) des Blocks, den ein Miner gefunden hat, an eine Taproot-Adresse zu senden. Taproot erhöht Flexibilität und Privatsphäre von Transaktionen und lässt sich in jede Art von Output integrieren, auch in die Outputs einer Coinbase-Transaktion.

  • Erzeugen einer Taproot-Adresse: Der Miner oder, typischer, der Mining-Pool erzeugt eine Taproot-Adresse. Dazu wird ein Schnorr-Public-Key erstellt, der optional zusätzliche Script-Bedingungen für komplexere Ausgabeszenarien enthalten kann.
  • Erstellen der Coinbase-Transaktion: In der Coinbase-Transaktion wird der Output auf die Taproot-Adresse gesetzt. Das scriptPubKey-Feld des Outputs sähe etwa so aus: OP_1 <Taproot public key>.
  • Minen des Blocks: Sobald der Block erfolgreich gemined ist, wird die Coinbase-Transaktion samt ihrem Output an die Taproot-Adresse in der Blockchain bestätigt.
  • Reifezeit der Block-Belohnung: Wie bei jeder Coinbase-Transaktion sind die ausgeschütteten Bitcoin wegen der Reifeanforderung (Maturity) des Bitcoin-Protokolls erst 100 Blöcke später ausgebbar.
  • Ausgeben von der Taproot-Adresse: Nach Ablauf der Reifezeit können die Bitcoin von der Taproot-Adresse ausgegeben werden, entweder über den Key-Path für einfache Single-Signature-Transaktionen oder über den Script-Path für komplexere Bedingungen, falls solche eingerichtet sind.

Durchgerechnetes Beispiel: Alice, Bob und andere in einem Pool

Dieses Beispiel nutzt sowohl den Key-Path als auch den Script-Path von Taproot, um Belohnungen nach bestimmten Bedingungen zu verteilen.

Schritt 1 – Erzeugen der Taproot-Adresse. Alice, Bob und andere einigen sich auf Bedingungen, unter denen sie ihren Anteil an den Mining-Belohnungen erhalten. Sie erstellen eine Taproot-Adresse, die ihre Public Keys und alle für komplexere Verteilungen nötigen Scripts kombiniert.

Schritt 2 – Einrichten der Coinbase-Transaktion. Output 1 zahlt an eine Taproot-Adresse mit einem Key-Path (eine einzelne Signatur eines Hauptschlüssels, möglicherweise vom Pool-Betreiber gehalten, für eine einfache Verteilung, wenn alle Parteien zustimmen) und einem Script-Path (Scripts für verschiedene Verteilungen, z. B. erhält Alice 40 %, Bob 30 %, und die anderen teilen sich die übrigen 30 % nach ihren vereinbarten Bedingungen).

Beispiel für das Transaktions-Script:

Key-path output:    OP_1 <combined Schnorr public key>
 Script-path output: Uses MAST to hide individual conditions where:
  - Alice's condition could be based on time or block height for her shares.
  - Bob's condition might involve his active participation in mining over a period.
  - Others have their script based on other criteria like electricity contributions.

Schritt 3 – Minen des Blocks. Sobald der Block gemined ist, wird die Coinbase-Transaktion mit der obigen Struktur bestätigt, und der Block wird der Blockchain hinzugefügt.

Schritt 4 – Verteilung der Belohnungen. Key-Path-Spend: Sind alle Bedingungen standardmäßig und unstrittig, kann der Inhaber des Hauptschlüssels eine Transaktion signieren, die die Belohnungen nach einer vorab vereinbarten Formel verteilt. Script-Path-Spend: Müssen bestimmte Bedingungen erfüllt werden (etwa eine Streitbeilegung oder eine zeitgesteuerte Freigabe), werden die betreffenden, in der MAST-Struktur kodierten Scripts ausgeführt, um die Belohnungen entsprechend zu verteilen.

Schritt 5 – Reifezeit und Ausgabe. Die Belohnungen aus der Coinbase-Transaktion müssen 100 Blöcke lang reifen, bevor sie ausgegeben werden können. Danach erfolgt die Verteilung gemäß den ausgelösten Key-Path- oder Script-Path-Bedingungen.

Den Taproot-Hauptschlüssel geheim halten

Es ist möglich und mitunter vorzuziehen, dass der Taproot-Hauptschlüssel allen Beteiligten unbekannt bleibt, bis er in der Coinbase-Transaktion verwendet wird, insbesondere wenn der Hauptschlüssel vor allem einer bestimmten Funktion dient, etwa der Verteilung von Mining-Belohnungen, und seine Offenlegung zum Schutz von Sicherheit und Privatsphäre begrenzt wird.

Vertraulichkeit: Bleibt der Taproot-Hauptschlüssel bis zu seiner ersten Verwendung unbekannt, schützt das die Details der Vereinbarung und der Verteilungsformel vor vorzeitiger Offenlegung – vorteilhaft in einem kompetitiven Mining-Umfeld. Sicherheit: Wer die Offenlegung des Schlüssels begrenzt, verringert das Risiko unbefugten Zugriffs oder von Leaks; dieser Schlüssel kann bei seiner Verwendung erhebliche Mengen an Kryptowährung kontrollieren.

Umsetzung. Erzeugung: Der Schlüssel kann von einer vertrauenswürdigen Partei erzeugt werden oder in einem gemeinsamen Verfahren mit einem Protokoll wie MuSig, bei dem mehrere Parteien zur Erzeugung beitragen, ohne dass eine einzelne Partei den gesamten Schlüssel kennt. Verwendung: Der Schlüssel wird im Script der Taproot-Adresse innerhalb der Coinbase-Transaktion verwendet. Offenlegung: Der Schlüssel wird dem Blockchain-Netzwerk beim Signieren der Transaktion offengelegt, kann aber für die Parteien verborgen bleiben, wenn er für weitere Transaktionen nicht benötigt wird.

Hinweis, November 2026. Der 32-Byte-Output-Key selbst ist öffentlich: Er steht ab dem Moment, in dem der Block gemined wird, im Coinbase-Output. Privat bleiben können der interne Schlüssel und jedes Script-Leaf, das nie verwendet wird. Mit MuSig2 besitzt keine einzelne Partei jemals den privaten Schlüssel eines kombinierten Schlüssels.

In einem Mining-Pool-Szenario kann ein Taproot-Schlüssel, der bis zu seiner Verwendung allen Teilnehmern unbekannt ist, vereinbarte Verteilungsregeln durchsetzen, ohne jedem Miner die Einzelheiten offenzulegen, und Streitbeilegung oder bedingte Verteilungen ermöglichen, die in den Script-Paths kodiert sind und nur aktiviert werden, wenn bestimmte Bedingungen erfüllt sind.

Die Verteilung ohne den privaten Schlüssel überprüfen

Alice, Bob und andere können die Verteilung der Mining-Belohnungen einer Taproot-Adresse überprüfen, ohne den privaten Schlüssel zu kennen, da die Bitcoin-Blockchain öffentlich und transparent ist.

  • Transparenz des Public Keys: Auch wenn der private Schlüssel unbekannt ist, ist der zur Taproot-Adresse gehörende Public Key sichtbar und überprüfbar. Die Schnorr-Signaturen von Taproot ermöglichen Key Aggregation und eine datenschutzfreundlichere Script-Ausführung, erlauben aber weiterhin die öffentliche Überprüfung der beabsichtigten Transaktionsstrukturen.
  • Untersuchung der Scripts: Taproot-Adressen können MAST enthalten, die komplexe Scripts verbergen, welche erst bei Verwendung offengelegt werden müssen. Die Bedingungen, unter denen diese Scripts ausgeführt werden, können von Anfang an transparent gemacht werden, durch öffentliche Dokumentation oder die Vereinbarung eines kooperativen Pools.
  • Vorab-Festlegung der Bedingungen: Die Bedingungen der Belohnungsverteilung können vorab im Taproot-Script festgelegt werden. Während einzelne Scripts nur bei Verwendung offengelegt werden, kann der Hash dieser Scripts (Teil der Merkle-Root) geteilt und mit dem abgeglichen werden, was in der Blockchain festgeschrieben ist.
  • Simulation und Werkzeuge: Werkzeuge können Transaktionen anhand des Public Keys und der bekannten oder angenommenen Script-Bedingungen simulieren, ohne die Transaktionen auszuführen oder auf den privaten Schlüssel zuzugreifen.

In der Praxis würden die Teilnehmer vor dem Mining auf einem Block-Kandidaten das Taproot-Setup und die zugehörigen Scripts prüfen, mit Blockchain-Analysewerkzeugen verifizieren, dass Public Key und Script-Hashes den vereinbarten Bedingungen entsprechen, und durch Simulation oder vertragliche Vereinbarungen bestätigen, dass die Belohnungsverteilung ihren Erwartungen entspricht.

Umgang mit ungültigen Adressen in MAST

Versucht eine der ausgebenden Transaktionen in einem MAST-Setup, Mittel an eine ungültige Adresse zu senden, sind je nach Art der „ungültigen Adresse“ mehrere Szenarien denkbar:

  • Ungültiges Adressformat: Entspricht die Adresse keinem anerkannten Bitcoin-Adressformat, weigert sich die Wallet, die Transaktion zu erstellen (siehe den Hinweis unten).
  • Nicht existierende, aber gültige Adresse: Ist die Adresse technisch gültig, gehört aber zu keinem bekannten privaten Schlüssel, kann die Transaktion trotzdem verarbeitet und in einen Block aufgenommen werden – die Bitcoin wären praktisch verbrannt, da niemand den Schlüssel besitzt, um sie auszugeben.
  • Fehlschlag bei der Script-Auswertung: Wird die Adresse über ein Script abgeleitet, dessen Ausführung fehlschlägt, gilt die Transaktion als ungültig, sobald sie dieses Output-Script auszuführen versucht, und wird nicht bestätigt.

Hinweis, November 2026. Auf Protokollebene gibt es keine Adressen, nur Output-Scripts. Eine Adresse, die sich nicht dekodieren lässt, fängt die Wallet ab, bevor überhaupt eine Transaktion existiert. Ein Output-Script, das niemand erfüllen kann, ist in einem Block trotzdem gültig, und seine Coins sind verbrannt. Ein fehlerhaftes Script-Leaf schlägt erst fehl, wenn jemand versucht, damit auszugeben.

Umgang und Vorbeugung: Gut konzipierte Wallets und Knoten validieren Adressen vor dem Broadcast; Scripts innerhalb eines MAST sollten so gestaltet sein, dass sie sicher fehlschlagen; Scripts sollten vor dem Einsatz gründlich getestet und auditiert werden; und fortgeschrittene Setups können Wiederherstellungsbedingungen enthalten (mit sorgfältigem kryptografischem Design, um keine neuen Schwachstellen zu schaffen). Das Senden an eine ungültige Adresse führt typischerweise zur Ablehnung der Transaktion oder zum Verlust der Mittel; gründliche Prüfungen und Audits sind daher unerlässlich.

Grundlagen des Bitcoin-Minings, mit Taproot

Bitcoin-Mining ist der Vorgang, neue Transaktionen zur Blockchain hinzuzufügen; Miner lösen mit leistungsfähigen Computern Hash-Rätsel, und wer als Erster eine Lösung findet, darf einen Block anhängen und erhält die Belohnung. Da Mining viel Rechenleistung erfordert, schließen sich einzelne Miner oft Mining-Pools an, die ihre Rechenleistung bündeln; hat der Pool Erfolg, wird die Belohnung nach der beigetragenen Leistung unter den Mitgliedern verteilt.

Einbindung von Taproot: Für den Empfang der Mining-Belohnungen wird eine Taproot-Adresse erzeugt (der Einfachheit halber ein einzelner Public Key oder komplexe Bedingungen, verborgen in ihrem MAST). Wenn der Pool einen Block findet, kann die Coinbase die Belohnung an die Taproot-Adresse ausgeben – Key-Path für eine einfache Aufteilung, Script-Path für bedingte Anteile (nach Zeit oder beigetragener Leistung), die erst bei Bedarf offengelegt werden. Schon vor dem Mining auf einem Kandidaten können alle Mitglieder das Adress-Setup und das Verteilungs-Script überprüfen, um Fairness sicherzustellen, und Taproot erhöht Sicherheit und Privatsphäre, weil die Komplexität verborgen bleibt, solange die Bedingungen keine Offenlegung erfordern, während alle Transaktionen in der Blockchain überprüfbar bleiben.

Taproot mit P2Pool

Taproot in einen dezentralen Pool wie P2Pool einzubinden, erfordert wegen dessen dynamischer Natur Anpassungen. P2Pool hat ein dezentrales Modell (kein Pool-Betreiber; jeder Miner betreibt einen Knoten in einem Peer-to-Peer-Netzwerk), eine Share-Chain (eine zweite Blockchain, in der jeder Share ein Proof of Work ist, der zum Finden eines Hauptblocks beiträgt; Shares werden weit häufiger gefunden als Blöcke) und eine dynamische Teilnahme (Miner kommen und gehen ohne Registrierung, gemessen an den eingereichten Shares).

  • Dynamische Erzeugung von Taproot-Adressen: Jeder Miner könnte eine persönliche Taproot-Adresse mit einfachen Auszahlungsbedingungen (Key-Path) und bedingten Auszahlungen je nach fortlaufender Teilnahme (Script-Path) erzeugen; oder es gibt eine gemeinsame Taproot-Adresse, verwaltet über einen Konsensmechanismus, der sich an Änderungen der Beiträge und des Zustands der Share-Chain anpasst.
  • Verteilung der Belohnung: Wird ein Block gefunden, geht die Belohnung an die gemeinsame Taproot-Adresse; die Verteilung beruht auf den Daten der Share-Chain und spiegelt den Beitrag jedes Miners über ein gleitendes Fenster wider – fair und proportional zum Aufwand.
  • Dynamische Script-Ausführung: Im MAST eingebettete Bedingungen könnten die Verteilung automatisch an das gleitende Fenster der Share-Chain anpassen, Änderungen bei Mining-Leistung, Share-Häufigkeit und Teilnahme berücksichtigen und mit Teilnehmern umgehen, die hinzukommen oder gehen.
  • Dezentrale Überprüfung: Alle teilnehmenden Miner überprüfen Integrität und Fairness der Verteilung anhand der Blockchain und der Share-Chain.
  • Effizienz und Privatsphäre: Taproot legt bestimmte Scripts nur bei Bedarf offen, und Schnorr-Signaturen sind effizient in Größe und Verifikationszeit – vorteilhaft in einer Umgebung mit hoher Frequenz.

Hardwareseitige Begrenzung der Adressanzahl

Das Problem, dass Hersteller von Mining-Hardware die Zahl der nutzbaren Coinbase-Adressen begrenzen – eine Praxis, die den Einsatz solcher Hardware in dezentralen Pools wie P2Pool oder c2pool einschränken könnte –, lässt sich mit Taproot allein nicht vollständig lösen. Taproot kann mehrere Ausgabebedingungen unter einer einzigen Adresse bündeln (über MAST und Schnorr), den Bedarf an mehreren Adressen verringern und Privatsphäre und Effizienz verbessern – sodass eine begrenzte Zahl von Adressen weiter reicht. Der Kern des Problems betrifft aber Herstellerrichtlinien, die Kontrolle über die Hardware und die Autonomie der Miner:

  • Einschränkungen der Hardware-Firmware: Ist die Firmware auf bestimmte Adressen festgelegt oder schränkt sie die Adressfunktionen ein, bleiben die Möglichkeiten von Taproot ohne Änderungen an Firmware oder Hardware womöglich ungenutzt.
  • Mitwirkung der Hersteller oder Richtlinienänderung nötig: Eine echte Veränderung würde wahrscheinlich einen Kurswechsel der Hersteller oder Druck aus der Community erfordern.
  • Alternative Lösungen: Miner könnten auf stärker quelloffene oder anpassbare Hardware ausweichen, bei der sie mehr Kontrolle über solche Einstellungen haben.

Taproot behandelt die Symptome – wie effizient und flexibel jede erlaubte Adresse genutzt werden kann –, nicht aber die Ursache, die vom Hersteller auferlegte Begrenzung der Adressanzahl. Mögliche Umgehungen sind die Wiederverwendung von Adressen über verschiedene Blöcke hinweg (sofern erlaubt), eine Adressverwaltung auf Pool-Ebene (eine einzige Taproot-Adresse pro Pool oder eine kleine Anzahl) und – wo rechtlich und ethisch vertretbar – Firmware-Änderungen; daneben ein breiteres Eintreten für offene Standards und die Beachtung rechtlicher, garantiebezogener und regulatorischer Folgen.

Taproot in c2pool heute

  • Der Litecoin-Knoten von c2pool setzt die Soft Forks segwit, taproot und mweb voraus, wie das Litecoin-Netzwerk.
  • Eine Taproot-Auszahlungsadresse wird auf der Litecoin-Share-Chain derzeit nicht unterstützt. Ein V36-Share enthält einen 20-Byte-Auszahlungs-Hash, ein P2TR- (oder P2WSH-)Output braucht aber 32 Bytes. c2pool akzeptiert einen solchen Login, doch die Litecoin-Auszahlung dieses Miners wird an andere Miner umverteilt (über den --redistribute-Modus des Knotens), mit einer Warnung im Log und „P2WSH/P2TR address → redistributed“ (Übersetzung: „P2WSH/P2TR-Adresse → umverteilt“) im Dashboard. Verwende eine P2PKH-, P2WPKH- oder P2SH-Adresse.
  • Für Merged Mining braucht c2pool für jeden Litecoin-Miner eine Dogecoin-Auszahlung. Dogecoin hat weder SegWit noch Taproot, daher zahlt c2pool an den Schlüssel der Litecoin-Adresse (P2PKH und P2WPKH als P2PKH, P2SH als P2SH), es sei denn, der Miner gibt im Stratum-Login ausdrücklich eine Dogecoin-Adresse an (LTC_ADDRESS,DOGE_ADDRESS).
V37Viele Miner, eine Coinbase, ohne Betreiberschlüssel.

Die obigen Setups stützen sich auf einen Taproot-Schlüssel, „möglicherweise vom Pool-Betreiber gehalten“, und auf MAST, um viele Bedingungen in einen Output zu packen. Ein Key-Path, den ein Betreiber hält, ist eine verwahrende (custodial) Struktur, die ein dezentraler Pool vermeiden muss. Die Bündelung per MAST kann außerdem keine unbegrenzte Zahl von Minern aus einer Coinbase begrenzter Größe bezahlen.

Eine frühere Fassung dieses Kastens beschrieb eine Abhilfe, bei der Minern Salden geschuldet würden, die in einem gemeinsamen Ledger geführt und in späteren Blöcken ausgezahlt werden. Dieses Modell ist zurückgezogen: Eine unabhängige Prüfung hat gezeigt, dass ein Pool ohne Verwahrer nicht einigen Minern etwas schulden kann, ohne anderen zu viel auszuzahlen, und die Überzahlung wird nie zurückgeholt. Siehe die Errata vom 4. Oktober 2026 in der Zusammenfassung des Purple Paper; Abschnitt 9 des Papers ist als zurückgezogen markiert.

Taproot bleibt ein nützlicher Baustein: Jeder Output kann weiterhin ein Taproot-Schlüssel sein, für Privatsphäre und Effizienz. Für sich genommen ist das aber keine Antwort auf das Problem der Coinbase-Größe.
